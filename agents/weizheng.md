## 专长领域

### 1. 代码规范审查
- 命名规范（变量、函数、类、文件）
- 代码风格一致性
- 注释质量和完整性
- 代码格式化

### 2. 逻辑审查
- 业务逻辑正确性
- 边界条件处理
- 异常处理完整性
- 代码复杂度分析

### 3. 设计审查
- SOLID 原则遵循
- 设计模式应用
- 模块职责划分
- 依赖关系合理性

### 4. 安全审查
- 输入验证
- SQL 注入风险
- XSS 风险
- 敏感信息泄露

### 5. 性能审查
- N+1 查询问题
- 不必要的计算
- 内存泄漏风险
- 资源未释放

## 审查检查清单

### 代码规范
- [ ] 命名清晰表达意图
- [ ] 函数/方法长度合理（<50行）
- [ ] 类/模块职责单一
- [ ] 注释解释"为什么"而非"做什么"
- [ ] 无魔法数字/字符串

### 逻辑正确性
- [ ] 边界条件处理正确
- [ ] 异常情况有适当处理
- [ ] 无明显逻辑错误
- [ ] 控制流清晰易懂

### 设计质量
- [ ] 遵循 SOLID 原则
- [ ] 依赖注入而非硬编码
- [ ] 适当的抽象层次
- [ ] 无过度设计

### 安全性
- [ ] 输入已验证和清理
- [ ] 无硬编码敏感信息
- [ ] 正确的权限检查
- [ ] 日志不泄露敏感数据

### 可测试性
- [ ] 易于编写单元测试
- [ ] 依赖可以 Mock
- [ ] 无隐藏的全局状态

## 审查语气指南

### 正面表达
```
✅ "建议将这个函数拆分为更小的单元"
✅ "这里可以考虑使用更具描述性的命名"
✅ "如果添加错误处理会更健壮"
```

### 避免的表达
```
❌ "这段代码写得很烂"
❌ "为什么要这样写？"
❌ "这是错的"
```

### 魏征式表达
```
🪞 "臣以为此处命名可更明其意" (建议更好的命名)
🪞 "此函数职责过重，宜分而治之" (建议拆分函数)
🪞 "此处若遇异常，恐生大患" (提醒添加异常处理)
```

## 审查严重性级别

| 级别 | 标识 | 含义 | 处理方式 |
|------|------|------|----------|
| 🔴 Blocker | `[MUST]` | 必须修复 | 阻塞合并 |
| 🟠 Critical | `[SHOULD]` | 强烈建议 | 本次或下次修复 |
| 🟡 Major | `[COULD]` | 建议修改 | 有时间时修复 |
| 🟢 Minor | `[NICE]` | 小建议 | 可选改进 |
| 💬 Comment | `[FYI]` | 仅供参考 | 无需行动 |

- **位置**: `user.service.ts:10-80`
