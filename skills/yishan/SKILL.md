# 愚公移山循环 (Yishan Loop) v2.2

基于 oh-my-opencode 的 ultrawork 机制重新设计，支持**智能动态工作流**。

## 🆕 v2.2 智能模式自动选择

愚公移山现在支持**自动识别任务特征，智能选择最佳执行模式**！

### 🤖 自动模式触发 (新功能)

**无需手动选择模式**，系统会根据任务描述自动识别并选择：

| 任务特征 | 自动选择 | 触发示例 |
|----------|----------|----------|
| 多组件/全栈 | ⚡ 超级模式 | "构建全栈 Todo 应用" "实现前端+后端+数据库" |
| 批量/同类 | 🐝 蜂群模式 | "修复所有类型错误" "为每个组件添加测试" |
| 简单/省Token | 💰 节俭模式 | "简单修改一下" "省点 token" "用 haiku" |
| 通用任务 | ⛰️ 标准模式 | "实现用户登录功能" "重构认证模块" |

**自动触发关键词**:

| 模式 | 自动触发关键词 |
|------|---------------|
| ⚡ 超级模式 | `全栈`、`前端和后端`、`多模块`、`多组件`、`完整系统` |
| 🐝 蜂群模式 | `所有X`、`全部X`、`批量`、`每个`、`fix all`、`add to all` |
| 💰 节俭模式 | `简单`、`快速`、`省token`、`用haiku`、`小改动` |
| ⛰️ 标准模式 | 其他所有任务（默认） |

### ⚠️ 模式优先级规则

当任务描述同时匹配多个模式的关键词时，按以下优先级选择：

```
⚡ 超级模式 > 🐝 蜂群模式 > 💰 节俭模式 > ⛰️ 标准模式
```

**示例**：
- "全栈应用修复所有错误" → 匹配超级+蜂群 → **选择超级模式**（并行更高效）
- "批量修复简单的类型错误" → 匹配蜂群+节俭 → **选择蜂群模式**（批量优先）

**设计原则**：优先选择能最大化并行度的模式，因为并行带来的效率提升通常大于成本节省。

### 📝 手动模式选择

仍可通过命令显式指定模式：

```bash
# 超级模式 - 并行加速
/chaoji 构建全栈应用
/ultrapilot build fullstack app

# 节俭模式 - 省 Token
/jiejian 添加表单验证
/ecomode fix login bug

# 蜂群模式 - 批量处理
/fengqun 5:luban "修复所有 TypeScript 错误"
/swarm 3:baozheng "为所有服务添加测试"

# 标准模式 - 通用
/yishan 实现用户登录功能
```

## 核心理念

> **不是机械走流程，而是智能达目标。**

- 任务驱动：根据任务类型决定需要哪些 Agent
- 按需循环：测试失败就修复，修复后再测试
- 智能退出：满足质量标准才能退出
- 代码清洁：完成后清理测试产物，保持代码库整洁

### 任务类型自动识别

启动时，愚公会分析任务并决定需要哪些阶段：

| 任务类型 | 自动启用的阶段 | 示例 |
|---------|---------------|------|
| **Bug 修复** | 探索 → 诊断 → 修复 → 测试 → 清理 | "修复登录报错" |
| **新功能** | 需求 → 探索 → 设计 → 实现 → 测试 → 清理 | "添加用户注册" |
| **重构** | 探索 → 设计 → 实现 → 测试 → 审查 → 清理 | "重构认证模块" |
| **性能优化** | 探索 → 分析 → 优化 → 测试 → 清理 | "优化查询性能" |
| **简单修改** | 实现 → 测试 → 清理 | "修改按钮文字" |

### 阶段跳过规则

**【重要】** 不是每个任务都要走完整流程：

```
简单任务（< 30分钟）：
  ✓ 实现 → 测试 → 清理
  ✗ 跳过：需求分析、架构设计、性能优化

中等任务（30分钟 - 2小时）：
  ✓ 探索 → 实现 → 测试 → 修复循环 → 清理
  ✗ 跳过：详细需求分析、安全审计

复杂任务（> 2小时）：
  ✓ 全流程：需求 → 探索 → 设计 → 实现 → 测试 → 优化 → 审计 → 清理
```

## 测试-修复循环（核心机制）

### 循环规则

```
┌─────────────┐
│  编写测试   │ ← 包拯
└──────┬──────┘
       ↓
┌─────────────┐     失败
│  运行测试   │ ─────────┐
└──────┬──────┘          │
       │ 通过            ↓
       │         ┌─────────────┐
       │         │  诊断问题   │ ← 扁鹊
       │         └──────┬──────┘
       │                ↓
       │         ┌─────────────┐
       │         │  修复代码   │ ← 鲁班/扁鹊
       │         └──────┬──────┘
       │                │
       │                └────────→ 回到运行测试
       ↓
┌─────────────┐
│  测试通过   │
└─────────────┘
```

### 最大循环限制

为防止无限循环，设置上限：

| 情况 | 最大循环次数 | 超过后行为 |
|------|-------------|-----------|
| 单个测试修复 | 5 次 | 请求用户介入 |
| 整体测试套件 | 10 次 | 暂停并报告 |

## 代码清理阶段（强制）

### 清理内容

**【NON-NEGOTIABLE】** 完成后必须清理：

| 清理项 | 说明 |
|-------|------|
| 调试代码 | `console.log`、`debugger`、`print` 等 |
| 临时文件 | 测试过程中生成的临时文件 |
| 注释掉的代码 | 删除而非注释 |
| 未使用的导入 | 清理 dead imports |
| 测试数据 | 清理硬编码的测试数据 |

### 清理检查清单

```text
📋 代码清理检查

□ 无调试语句 (console.log/debugger/print)
□ 无注释掉的代码块
□ 无未使用的变量/导入
□ 无临时测试文件
□ 无硬编码测试数据
□ 代码格式统一 (运行 formatter)
□ 类型检查通过 (如适用)
```

## 退出条件（智能判断）

### 标准退出条件

愚公在以下条件**全部满足**时才能退出：

```
✅ 退出检查清单

1. 功能完成
   □ 所有 TODO 标记为 completed
   □ 用户需求已实现

2. 质量达标
   □ 所有测试通过（如有）
   □ 构建成功（如适用）
   □ 无 TypeScript/ESLint 错误（如适用）

3. 代码清洁
   □ 清理检查清单已完成
   □ 无调试代码残留
   □ 代码已格式化

4. 验证通过
   □ 手动验证功能正常（如需要）
   □ 无回归问题
```

### 不允许的退出情况

| 情况 | 为什么不能退出 |
|------|---------------|
| "测试应该能通过" | 没有证据，必须运行 |
| "我修复了 bug" | 没有验证，必须测试 |
| TODO 还有 pending | 任务未完成 |
| 有调试代码残留 | 代码不干净 |
| 构建失败 | 基本质量不达标 |

## Agent 分层体系 (v2.2 新增)

为支持节俭模式，所有主要 Agent 现在都有分层版本：

| Agent | LOW (Haiku) | MEDIUM (Sonnet) | HIGH (Opus) |
|-------|-------------|-----------------|-------------|
| 诸葛 | zhuge-low | zhuge | zhuge-high |
| 鲁班 | luban-low | luban | - |
| 包拯 | baozheng-low | baozheng | - |
| 扁鹊 | bianque-low | bianque | - |
| 顾恺之 | gukaizhi-low | gukaizhi | - |
| 墨子 | mozi-low | mozi | - |
| 仓颉 | cangjie-low | cangjie | - |

**分层选择原则**：
- 简单任务 → 先用 LOW，失败再升级
- 标准任务 → 直接用 MEDIUM
- 复杂任务 → 必要时用 HIGH
