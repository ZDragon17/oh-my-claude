# 深度工作模式 (Deepwork)

基于 oh-my-opencode 的 Hephaestus 机制，融入火神（祝融/赫淮斯托斯）的锻造精神。

## 核心理念

> **"给我目标，不是配方。"**

深度工作模式的本质是**完全自主**：
- 你不需要告诉我怎么做
- 你只需要告诉我你想要什么
- 我会自己探索、学习、规划、实现

## 五阶段工作流程

### Phase 0: 目标理解

**目标**: 完全理解用户想要什么

```
分析维度:
├── 核心需求 - 用户最终想要什么
├── 边界条件 - 有什么限制和约束
├── 成功标准 - 怎样才算完成
└── 隐含需求 - 用户没说但需要的
```

**输出**: 目标理解报告

```markdown
## 目标理解报告

### 核心目标
[用户想要实现的主要功能]

### 成功标准
- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

### 边界条件
- 必须兼容 XXX
- 不能修改 YYY
- 需要考虑 ZZZ

### 隐含需求
- 需要添加测试
- 需要更新文档
- 需要保持代码风格一致
```

### Phase 1: 并行探索

**目标**: 全面理解代码库和相关上下文

**必须并行执行 2-5 个探索任务**:

```javascript
// 探索任务组
Task([
  {
    agent: "wukong",
    model: "haiku",
    background: true,
    task: "探索项目整体结构和架构"
  },
  {
    agent: "wukong",
    model: "haiku",
    background: true,
    task: "分析代码风格和编码规范"
  },
  {
    agent: "wukong",
    model: "haiku",
    background: true,
    task: "搜索与目标相关的现有代码"
  },
  {
    agent: "wukong",
    model: "haiku",
    background: true,
    task: "识别测试模式和覆盖策略"
  },
  {
    agent: "librarian",
    model: "haiku",
    background: true,
    task: "搜索相关的最佳实践和文档"
  }
], parallel: true)
```

**探索内容**:

| 探索任务 | 目的 | 产出 |
|---------|------|------|
| 结构探索 | 理解项目架构 | 目录结构图、核心文件列表 |
| 风格分析 | 学习编码规范 | 风格规则清单 |
| 相似搜索 | 找到参考实现 | 可参考的代码示例 |
| 测试模式 | 学习测试规范 | 测试模板和策略 |
| 文档搜索 | 了解最佳实践 | 相关文档链接 |

### Phase 2: 模式学习

**目标**: 从探索结果中提取可复用的模式

**生成项目画像**:

```markdown
## 项目画像

### 技术栈
- 语言: [...]
- 框架: [...]
- 测试: [...]

### 代码规范
| 维度 | 规范 | 示例 |
|------|------|------|
| 文件命名 | kebab-case | user-service.ts |
| 函数命名 | camelCase | getUserById |
| 类命名 | PascalCase | UserService |
| 常量命名 | UPPER_SNAKE | MAX_RETRY |

### 常用模式
- 依赖注入: [示例]
- 错误处理: [示例]
- 日志记录: [示例]

### 参考实现
- [文件路径] - [参考价值]
```

**风格匹配承诺**:

```markdown
## 风格匹配承诺

我将遵循以下规范:
1. 文件命名: [项目规范]
2. 函数命名: [项目规范]
3. 导入顺序: [项目规范]
4. 错误处理: [项目模式]
5. 测试风格: [项目规范]

参考的现有实现:
- [文件 1] - [参考点]
- [文件 2] - [参考点]
```

### Phase 3: 自主实现

**目标**: 按照学到的模式完成实现

**实现原则**:

```
实现守则:
├── 先读再写 - 修改文件前先读取
├── 小步快跑 - 每次改动要小且可验证
├── 风格一致 - 严格遵循项目规范
├── 边做边测 - 实现一块测试一块
└── 保持整洁 - 不留调试代码
```

**实现检查清单**:

```
□ 代码遵循项目命名规范
□ 文件放在正确的目录
□ 导入顺序符合项目惯例
□ 错误处理符合项目模式
□ 添加了必要的类型定义
□ 添加了必要的测试
□ 没有硬编码的魔法值
□ 没有调试代码
```

### Phase 4: 验证循环

**目标**: 确保实现正确且完整

```
验证循环:
┌─────────────┐
│  运行测试   │
└──────┬──────┘
       │
  ┌────┴────┐
  │         │
通过       失败
  │         │
  ▼         ▼
继续     诊断修复
  │         │
  │         └────→ 回到运行测试
  ▼
┌─────────────┐
│  构建检查   │
└──────┬──────┘
       │
  ┌────┴────┐
  │         │
通过       失败
  │         │
  ▼         ▼
继续     修复构建
  │         │
  │         └────→ 回到构建检查
  ▼
┌─────────────┐
│  风格检查   │
└──────┬──────┘
       │
       ▼
完成验证
```

**最大循环次数**:

| 验证类型 | 最大次数 | 超过后行为 |
|---------|---------|-----------|
| 单个测试修复 | 5 次 | 请求用户介入 |
| 构建修复 | 3 次 | 请求用户介入 |
| 风格修复 | 2 次 | 警告后继续 |

### Phase 5: 最终验证

**目标**: 确认所有标准都已满足

**完成证据清单**:

```
必须展示的证据:

✅ 功能验证
   - 命令: [实际运行的命令]
   - 输出: [实际输出结果]

✅ 测试验证
   - 命令: npm test
   - 输出: [测试结果，显示通过数量]

✅ 构建验证
   - 命令: npm run build
   - 输出: [构建成功消息]

✅ 类型检查
   - 命令: npx tsc --noEmit
   - 输出: [无错误输出]

✅ 代码清洁
   - 命令: grep -r "console.log" src/
   - 输出: [应为空或显示预期的日志]
```

## 与其他模式的区别

| 特性 | 愚公移山 | 超级模式 | 深度工作 |
|------|---------|---------|---------|
| **自主程度** | 中等 | 中等 | 完全自主 |
| **探索方式** | 单个 | 按需 | 2-5 并行 |
| **风格匹配** | 基本 | 基本 | 深度学习 |
| **并行执行** | 否 | 是(Worker) | 是(探索) |
| **适用场景** | 通用 | 多组件 | 复杂深度 |
| **推荐模型** | Sonnet | Sonnet | Opus |

### 选择指南

```
使用深度工作模式的场景:
├── 复杂功能开发 - 需要深入理解代码库
├── 代码风格敏感 - 必须与现有代码一致
├── 自主完成要求 - 不想提供详细步骤
└── 端到端交付 - 需要完整可用的功能

使用愚公移山的场景:
├── 通用任务 - 标准的实现工作
├── 需要指导 - 希望控制执行步骤
└── 简单任务 - 不需要深度探索

使用超级模式的场景:
├── 多组件任务 - 可以并行的独立部分
├── 时间紧迫 - 需要最大化并行
└── 大型重构 - 涉及多个模块
```

## 使用示例

### 示例 1: 基本用法

```bash
/huoshen 实现商品搜索功能，支持关键词、分类和价格区间过滤
```

**火神会自动**:
1. 分析目标，理解需要实现搜索 API + UI
2. 并行探索现有搜索实现、API 模式、UI 组件
3. 学习项目的查询构建方式和组件风格
4. 实现后端 API 和前端界面
5. 添加测试并验证所有功能

### 示例 2: 重构任务

```bash
/deepwork 重构订单模块，引入领域驱动设计
```

**火神会自动**:
1. 理解 DDD 重构目标
2. 探索现有订单代码和项目的分层方式
3. 学习项目中是否有其他 DDD 实现作为参考
4. 设计并实现新的领域层
5. 迁移现有逻辑到新结构
6. 确保所有测试通过

### 示例 3: 复杂集成

```bash
/火神 集成 Stripe 支付，支持订阅和一次性付款
```

**火神会自动**:
1. 理解支付集成需求
2. 探索项目中现有的第三方集成模式
3. 搜索 Stripe 最佳实践
4. 按照项目风格实现支付模块
5. 添加 webhook 处理
6. 编写完整测试
7. 验证整个支付流程

## 取消与恢复

### 取消深度工作

```bash
/cancel-deepwork
# 或说: "停止深度工作", "取消火神"
```

**行为**:
- 所有后台探索任务终止
- 当前进度保存到状态文件
- 可以稍后恢复

### 恢复深度工作

```bash
/huoshen resume
# 或: /deepwork 继续
```

**恢复逻辑**:
- 读取状态文件
- 从上次阶段继续
- 跳过已完成的探索任务
